English only, like the tool directory it belongs to (see
[`../../README.md`](../../README.md)). The bilingual write-up, with the result
table and the limits of this measurement, is the section "Effective Processing
Rate" in
[docs/en/s3ap-throughput-benchmark.md](../../../../docs/en/s3ap-throughput-benchmark.md)
([日本語](../../../../docs/ja/s3ap-throughput-benchmark.md)). The read-latency

[`../2026-10-10-pooled/`](../2026-10-10-pooled/README.md),
[`../2026-10-11-tier/`](../2026-10-11-tier/README.md), and the three tiering-path

poller's work (read + parse), not delivery to a vendor.

## Files

Each file under `raw/` is the benchmark Lambda's `process`-mode response for one
size class. No value was edited or masked when the files were added to the
repository. A search of every file in this directory found no account ID, ARN,
access point alias, bucket name, resource ID, or IP address. The files hold
object keys, sizes, event counts, timings, run IDs, the Region, and per-object
samples.

| File | Content |
|------|---------|
| `raw/proc-5KB.json` | 10 objects of 5,536 B (11 audit events each), 5 iterations per object. Per-object `read_samples_ms` and `parse_samples_ms` in read order, plus a `per_size_class` summary |
| `raw/proc-200KB-50.json` | 50 objects of 205,234 B (412 events each), 5 iterations per object |
| `raw/proc-200KB-100.json` | 100 objects of 205,234 B (412 events each), 5 iterations per object |
| `raw/proc-2MB.json` | 10 objects of 2,097,634 B (4,212 events each), 3 iterations per object (see the deviation below) |
| `invocations.jsonl` | 4 lines, one per invocation: `tag`, `prefix`, the key limit, `iterations`, `start_utc`, `elapsed_s` (client side), `cli_rc`, `cli_out`, `cli_err` |
| `manifest.txt` | The uploaded objects, tab separated: `proc`, key, size in bytes. The 2 MB prefix (`c2mb/`) lists 100 uploaded objects even though the measurement read 10 of them (deviation below) |
| `run-notes.tsv` | Environment fields: Region, file system type, throughput capacity, Lambda memory, Lambda VPC placement, concurrency, ONTAP version, date, parser path, input description |

## Run IDs and schedule

`benchmark_run_id` is the invocation `tag`: `proc-5KB`, `proc-200KB-50`,
`proc-200KB-100`, `proc-2MB`. The `process` mode reads each object the stated
number of iterations and times the read leg (GetObject) and the parse leg
(`parse_audit_log`) separately, at concurrency 1.

| Tag | Prefix | Objects x iterations | Start (UTC) | Client elapsed |
|-----|--------|----------------------|-------------|----------------|
| `proc-5KB` | `c5kb/` | 10 x 5 | 2026-10-11T21:54:15Z | 4.43 s |
| `proc-200KB-50` | `c200-50/` | 50 x 5 | 2026-10-11T21:54:20Z | 42.03 s |
| `proc-200KB-100` | `c200-100/` | 100 x 5 | 2026-10-11T21:55:02Z | 86.54 s |
| `proc-2MB` | `c2mb/` | 10 x 3 | 2026-10-11T22:10:19Z | 55.71 s |

## Deviation

The 2 MB class was measured on 10 files x 3 iterations (30 reads), not the
100 files x 5 iterations used for the other classes. The first attempt at
100 x 5 (500 reads of about 2 MB) exceeded the 290 s client-side read timeout
and returned no result; the event files for 100 objects were already uploaded,
which is why `manifest.txt` lists 100 objects under `c2mb/`. The read leg and the
parse leg are per-object, so the file count does not change their p50; the
10 x 3 run (55.7 s) is a valid per-object sample. Only the per-invocation
duration figure for the 100 x 2 MB scenario is derived (read+parse p50 x 100),
not timed end to end.

## Environment

The fields are in `run-notes.tsv`. Region ap-northeast-1. One existing
SINGLE_AZ_1 (first generation) Amazon FSx for NetApp ONTAP file system with
128 MBps throughput capacity and 1024 GiB SSD. One disposable volume
(1024 then 2048 MiB, UNIX security style, tiering policy NONE, auditing off) on
the `verification-svm` SVM, with one S3 Access Point (type ONTAP, internet
origin). ONTAP 9.19.1P2, read through the ONTAP REST API. The client was the
[benchmark tool](../../README.md), deployed as a Lambda function with 256 MB
memory and a 300 s timeout, outside a VPC, so it reached the S3 Access Point
over the internet origin. Concurrency 1. The parser is the committed
`shared/python/ontap_audit_parser.py` (`parse_audit_log`). The input objects are
a fixture ONTAP XML `<Event>` repeated to the target byte size, generated by the
upload script (not committed). The volume, the S3 Access Point, and the stack
were deleted afterwards; the recovery queue was purged. The file system and its
other volumes and S3 Access Points were not changed.

## How to read the figures

`read_samples_ms` and `parse_samples_ms` hold each object's per-iteration
latencies in read order. The class-level `p50_ms` in `per_size_class` is the
median by nearest rank over the pooled samples of all objects in that class, the
tool's `percentile_method` `"pooled_nearest_rank"`. Read+parse p50 is the sum of
the class read p50 and the class parse p50. The per-invocation duration is that
read+parse p50 times the file count of the scenario, at concurrency 1
(sequential), with delivery to a vendor excluded. These are latencies observed
in this environment on this date, not a service limit.

## Recomputing

The script needs Python 3 and reads only the four files under `raw/`. Run it
from any directory:

```bash
python3 analyze_processing_rate.py > /tmp/analysis-output.txt
diff /tmp/analysis-output.txt analysis-output.txt
```

The `diff` prints nothing when the committed output matches. The script also
asserts that each recomputed class p50 equals the value stored in the file.
