## 目的

本ドキュメントは、S3 Access Points 経由で Amazon FSx for NetApp ONTAP の監査ログを読み取る際のベンチマーク手法と参考結果を提供します。これらの結果は**サイジングの参考値であり、サービス上限ではありません**。

「本リポジトリでの実測（2026-10-10）」「プール集計による再測定（2026-10-10）」「階層別の比較: SSD とキャパシティプール（2026-10-11）」の 3 つの節が、このリポジトリにある、S3 Access Points 読み取りレイテンシの唯一の測定です。生データは、1 つ目が `benchmark/s3ap-throughput/results/2026-10-10/`（平均方式）、2 つ目が `benchmark/s3ap-throughput/results/2026-10-10-pooled/`（プール集計）、3 つ目が `benchmark/s3ap-throughput/results/2026-10-11-tier/`（階層化ポリシーが NONE と ALL のボリューム、解析スクリプト付き）にコミットしています。位置の確認は 2 つ目の節の中の小節群で、生データは `benchmark/s3ap-throughput/results/2026-10-10-position/` にコミットしています。「参考結果」の節の値は、姉妹リポジトリからの転記です。

> **注意**
>
> 結果は以下に記載するテスト環境に固有のものです。実際のスループットは、FSx スループットキャパシティ、オブジェクトサイズ分布、ネットワーク経路、同時実行数、ワークロード構成によって異なります。必ず自身の環境で検証してください。

## 測定方法

### テストスクリプト

下のスクリプトは測定方法の例示です。2026-10-10 の数値を出したのは `benchmark/s3ap-throughput/` に収録したツールの当時の版で、スクリプトとは、数値の読み方に関わる 2 点が違います。p50 と p99 を `statistics.median` と `int(iterations * 0.99)` の添字ではなく nearest-rank 法で求めること、オブジェクトごとの結果に加えてサイズ区分ごとの集計を返すことです。

```python
"""S3 AP throughput benchmark for FSx for ONTAP audit logs.

Run from Lambda or EC2 in the same region as the S3 Access Point.
"""

import time
import statistics
import boto3

s3 = boto3.client("s3")

S3_AP_ARN = "arn:aws:s3:ap-northeast-1:123456789012:accesspoint/fsxn-audit-ap"
PREFIX = "audit/svm-prod-01/2026/05/"


def benchmark_list_objects(iterations: int = 10) -> dict:
    """Measure ListObjectsV2 latency."""
    latencies = []
    for _ in range(iterations):
        start = time.perf_counter()
        s3.list_objects_v2(Bucket=S3_AP_ARN, Prefix=PREFIX, MaxKeys=100)
        latencies.append((time.perf_counter() - start) * 1000)
    return {
        "operation": "ListObjectsV2",
        "iterations": iterations,
        "p50_ms": statistics.median(latencies),
        "p99_ms": sorted(latencies)[int(iterations * 0.99)],
        "mean_ms": statistics.mean(latencies),
    }


def benchmark_get_object(keys: list[str], iterations: int = 5) -> dict:
    """Measure GetObject latency and throughput by object size."""
    results = []
    for key in keys:
        latencies = []
        sizes = []
        for _ in range(iterations):
            start = time.perf_counter()
            resp = s3.get_object(Bucket=S3_AP_ARN, Key=key)
            body = resp["Body"].read()
            latencies.append((time.perf_counter() - start) * 1000)
            sizes.append(len(body))
        avg_size = statistics.mean(sizes)
        avg_latency = statistics.mean(latencies)
        throughput_mbps = (avg_size / 1024 / 1024) / (avg_latency / 1000) if avg_latency > 0 else 0
        results.append({
            "key": key,
            "size_bytes": int(avg_size),
            "p50_ms": statistics.median(latencies),
            "p99_ms": sorted(latencies)[min(int(iterations * 0.99), iterations - 1)],
            "throughput_mbps": round(throughput_mbps, 2),
        })
    return results
```

### オブジェクトサイズカテゴリ

| カテゴリ | 一般的なサイズ | 説明 |
|----------|-------------|-------------|
| Small | 1-10 KB | 単一監査イベント（JSON） |
| Medium | 100 KB - 1 MB | ローテーション済み監査ログファイル（典型的） |
| Large | 1-5 MB | 高アクティビティ期間のログファイル |

## 本リポジトリでの実測（2026-10-10）

> **測定上の注意**: この節は先の 2026-10-10 の測定です。平均方式を使ったため、p99 は「プール集計による再測定（2026-10-10）」の p99（プールした 120 サンプルの nearest-rank 法の値）と比較できません。この節の区分の p99 は、オブジェクトごとの p99 3 個の平均で、オブジェクトごとの p99 は 10 サンプルのうち最大の値です。裾のレイテンシは、プール集計の節の値を参照し、参考値として読んでください。

根拠区分は `verified` で、対象は次の 1 文だけです。上記「テスト環境」で、2026-10-10 に、これらのレイテンシを観測しました。他のファイルシステム、同時実行数、ネットワーク経路、日付には及びません。測定は同じ日に約 20 分あけて 2 回取りました（生データの時刻は UTC の 08:09 と 08:29）。したがって数値は安定値ではなく、観測した幅を示します。

ボリュームの階層化ポリシーは AUTO、クーリング期間は 31 日で、テストオブジェクトは読み取りの数分前に書き込んでいます。このため、読み取りは SSD（プライマリ階層）から返されたと推定しています。これはポリシーとオブジェクトの経過時間からの推定で、実行中に階層別の容量メトリクスは取得していません。

### 集計方法

各オブジェクトを 10 回、順番に読みました（同時実行数 1）。ListObjectsV2 は 20 回呼び、MaxKeys は上書きしていないのでツールの既定値 100 が効いています。この測定を行った版のツールは、オブジェクトごとに nearest-rank 法の p50・p99 と平均を計算しました。下表のサイズ区分ごとの p50 と p99 は、3 個のオブジェクトそれぞれの p50 と p99 の単純平均です。プールした 30 サンプルのパーセンタイルではありません。後続の版のツールは、区分ごとの値をプールしたサンプルから計算し、各区分に `percentile_method: "pooled_nearest_rank"` を付けます（[#147](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/issues/147)）。`results/2026-10-10/` の生データにこのキーはありません。後述のプール集計による再測定は、このような版で取りました。そのため、後続の版が出す区分の値は、この節の表と直接は比較できません。オブジェクト 1 個のスループットはそのオブジェクトの平均レイテンシとサイズから求め、区分の値は 3 個の平均です。ここでの MB/s は、ツールと同じく MiB/s（サイズを 1,048,576 バイトで割った値）です。

### この測定の限界

- p99 は参考値にとどまります。オブジェクトごとの p99 は 10 サンプルの最大値で、ListObjectsV2 の p99 は 20 サンプルの最大値です。実行 2 の 5 MB 区分の p99（444.951 ms）は、3 個のオブジェクトの最大値（152.683、361.481、820.689 ms）の平均で、1 個のオブジェクトの 1 回の遅い読み取りが大半を決めています。生データは要約のみでイテレーションごとのサンプルを残していないため、遅いサンプルの原因は後から確認できません。
- 2 回の測定では統計的な安定性は示せません。分散、信頼区間、安定した p99 のいずれも主張しません。
- ListObjectsV2 の測定では、12 個のテストオブジェクトに加えて、既存の大きなファイル（約 103 MiB）が 1 個同じプレフィックスにあり、13 キーを列挙しました。GetObject の測定はサイズごとに別のプレフィックスを使ったため影響を受けていません。13 キーの列挙結果は、キー数がもっと多いディレクトリについては何も示しません。
- スループットは同時実行数 1 の 1 ストリームあたりの値で、平均レイテンシとオブジェクトサイズから求めています。ファイルシステムのスループット上限ではなく、並列読み取りについても何も示しません。1 KB の値は帯域ではなくリクエストのレイテンシを反映しています。
- ツールは Lambda のコールドスタートの影響を分けていません。最初の ListObjectsV2 のサンプルや各呼び出しの最初のリクエストには、接続の確立が含まれている可能性があります。保存した要約からは、最大値が最初の呼び出しだったかどうかは分かりません。
- 対象外: 同時実行数 2 以上、VPC 内の Lambda や NAT 経由の経路（後述「ネットワーク経路」のレイテンシ差はこの測定から導いたものではありません）、他の Lambda メモリサイズ、他のスループットキャパシティ、第 2 世代やマルチ HA ペアのファイルシステム、より大きなディレクトリ。
- この測定の対象外: 階層化ポリシーが ALL のボリューム、およびすでにキャパシティプールへ階層化されたデータ。これらは後の測定で、3 種類のオブジェクトサイズ、同時実行数 1、1 つのファイルシステムについて測定しました。「階層別の比較: SSD とキャパシティプール（2026-10-11）」を参照してください。この節の値はキャパシティプールの値ではありません。

## プール集計による再測定（2026-10-10）

根拠区分は `verified` で、対象は次の 1 文だけです。上記「テスト環境」で、2026-10-10 に、3 回の測定（UTC の 14:55〜14:59）でこれらのレイテンシを観測しました。先の測定（UTC の 08:09〜08:29）と同じ日の後の時間帯で、区分ごとの値をプールしたサンプルから計算する版のツールを使っています。他のファイルシステム、リージョン、同時実行数、ネットワーク経路、日付には及びません。表は、見出しに「導出値」とあるものを除き、ツールの出力そのままです。導出値は、コミットした生データから計算した値で、ツールの出力ではありません。これは 1 つの環境でのサンプル実行の結果で、サイジングの参考値です。本番環境の見積りでも、サービス上限でもありません。

### 環境と先の測定との差

ファイルシステム、ボリューム、リージョン、Lambda の設定は「テスト環境」と同じです（SINGLE_AZ_1、スループットキャパシティ 128 MBps、HA ペア 1 組、1024 GiB。クライアントは同じリージョンの VPC 外にある 256 MB の Lambda）。ボリュームの階層化ポリシーは AUTO、クーリング期間は 31 日で、測定の前後に読み取り、値は同一でした。SSD 上にあったことは、ポリシーとオブジェクトの経過時間からの推定で、階層別の容量メトリクスは取得していません。ONTAP のバージョンは、この再測定では再確認していません。先の測定との違いは次のとおりです。

| 項目 | 先の測定（平均方式） | プール集計による再測定 |
|------|---------------------|------------------------|
| ツールの版 | 区分ごとの値を、オブジェクトごとのパーセンタイルの平均で出す版 | `main` のコミット `6808382` のツール（[#147](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/issues/147)） |

| オブジェクトあたりの読み取り回数 | 10 | 40 |

| S3 Access Points | タイプは ONTAP、インターネットオリジン、UNIX ユーザー `root` | 同じタイプ。この再測定のために新規に作成し、終了後に削除 |

### プール集計とサンプル数

- 区分ごとの値は、3 個のオブジェクト × 40 回 = 1 回の測定あたり 120 サンプルをプールし、nearest-rank 法で求めた値です。各区分に `percentile_method: "pooled_nearest_rank"` と `sample_count: 120` が付きます。
- オブジェクトごとの生のレイテンシは `per_object[].samples_ms` に残っています（オブジェクトあたり 40 個）。
- ListObjectsV2 は、1 回の測定につき 120 回呼んだ 1 系列です。結果に生サンプルを残さないため、ファイルから p99 を再計算できません。
- 120 サンプルの nearest-rank 法の p99 は、2 番目に大きいサンプルです。
- 読み取りは単一ストリームで逐次に行いました（同時実行数 1）。スループットは 1 ストリームあたりの値で、ファイルシステムの上限ではありません。MB/s は MiB/s です。
- 合計は読み取り 1,800 回（ListObjectsV2 が 360 回、GetObject が 1,440 回）で、GetObject で読んだデータは約 2.1 GiB です。

### 位置の確認: 100 回目の形と整合する第三者の報告

仮説であり、接続レベルでは確認していません。AWS SDK for Go v1 の公開 Issue（[aws/aws-sdk-go issue 2825](https://github.com/aws/aws-sdk-go/issues/2825)、2019 年）は、標準の S3 に対する PutObject と UploadPart の呼び出しで、1 本の HTTP 接続が 100 個のリクエストに使われ、101 個目のリクエストが新しい接続を開いたと報告しています。同じスレッドで、そのリポジトリの貢献者が、検証したうえで、これは AWS SDK for Go ではなく S3 の挙動のように見える（"looks to be a behavior of S3 rather than the AWS SDK for Go"）と書き、S3 は 1 本の接続で 100 個のリクエストを受けると接続を閉じる、と説明しました。報告者はその後、Wireshark のキャプチャで 100 個目の応答に `Connection: close` ヘッダーを確認しましたが、Go のクライアントが表示したヘッダーには見えず、別の貢献者は、Go の HTTP クライアントかトランスポートがそのヘッダーを取り除いているのではないかと推測しています。ここのツールは、同じクライアントで読み取りの前にキーを 1 回一覧取得するので、キーの一覧取得がリクエスト 1 個目で、100 回目の GetObject はリクエスト 101 個目です。ここでも同じことが起きているなら、100、200、300 回目に繰り返す遅い読み取りは、新しい接続の最初のリクエストということになります。この読み方は形と整合しますが、検証していません。別の SDK と別の操作についての、公開 Issue（2019 年）の利用者による報告と貢献者のコメントで、AWS のドキュメントではなく、この確認では接続やパケットのトレースを取っておらず、Lambda ランタイムの boto3 と urllib3 のバージョンも記録していません。この報告は、S3 Access Points での 50、150、250 回目の事象には触れていません。それらの出典は見つかっておらず、検索は網羅的ではありません。

## 階層別の比較: SSD とキャパシティプール（2026-10-11）

### 最初の呼び出しの前に固定した判定規則

サイズと読み取りクラスごとに、`m_A1(r)`、`m_A2(r)`、`m_B(r)` を測定 `r` の呼び出しの中央値とします。このとき:

- `D(r) = m_B(r) - (m_A1(r) + m_A2(r)) / 2`
- `N(r) = |m_A1(r) - m_A2(r)|`
- `N_largest` は、3 回の測定の `N(r)` のうち最大の値

そのサイズとクラスで B が遅いと言うのは、3 回の測定のすべてで `D(r) > 0` かつ `D(r) > N_largest` のときだけです。そうでなければ、差は確立できていません（`open`）。規則の対象は、初回読み取りのクラスと全読み取りのクラスです。反復読み取りは、規則なしで示します。規則は片側だけです。B のほうが速いかどうかは検定せず、そう主張することもしません。規則の文面は、このリポジトリにない計画ファイルに、最初の呼び出しの前に書きました。そのため、規則とデータの前後関係は、このリポジトリからは確認できません。

### 裏付けられる範囲と、裏付けられない範囲

この環境と 3 回の測定について、数値が裏付けるのは次のことです。

- 1 MiB と 5 MiB で、ALL のボリュームのオブジェクトの初回読み取りは、NONE のボリュームより中央値が高く、その差は 3 回とも A1 と A2 の差の最大より大きい。測定ごとの D は、1 MiB が +67.80〜+73.97 ms、5 MiB が +150.78〜+167.09 ms。3 回をまとめた初回読み取りの p50 は、1 MiB が A で 53.70 ms、B で 122.70 ms（+69.00 ms、2.3 倍）、5 MiB が A で 118.15 ms、B で 277.82 ms（+159.66 ms、2.4 倍）。
- キャパシティプールから読まれたバイト数は、1 回の呼び出しあたりオブジェクトのバイト数の約 1 パス分で、4 パス分ではない。これは、キャパシティプールに届くのが初回読み取りだけであることと整合する。
- B について、ボリューム別の `CapacityPoolReadOperations` は、どの測定でも、ノード別の `get` カウンタの増分と一致する。

数値が裏付けないのは次のことです。

- 64 KiB での差、およびどのサイズでも、初回読み取りと反復読み取りをまとめた場合の差。
- B の反復読み取りが SSD と同じ速さだという主張。9 つの測定×サイズのセルで、反復読み取りの D は -12.14〜+17.60 ms、A1 と A2 の差は 0.44〜16.89 ms で、規則はこのクラスを定義していません。3 回をまとめた反復読み取りの p50 の差は、1 MiB が +2.65 ms、5 MiB が +15.71 ms で、初回読み取りの +69.00 ms と +159.66 ms に対する値です。
- コストや請求の数値。
- 反復読み取りが速い理由、および 64 KiB の初回読み取りがキャパシティプールの読み取りを起こさなかった理由（`hypothesis`）。候補の 1 つは ONTAP 内のキャッシュです。検証しておらず、他の原因は除外していません。B のキャパシティプールのサイズは書き込んだ全量と等しいので、64 KiB のオブジェクトも階層化されていたと推測されます。

各オブジェクトを 1 回だけ読む読み手には、初回読み取りの値が対応します。全読み取りの値には、この読み手が行わない反復読み取りが含まれます。その読み手が読むオブジェクトがすでにキャパシティプールにあるかどうかは、ボリュームの階層化ポリシーと、書き込みから読み取りまでの時間に依存します。この測定では、その時間は 6.5〜52.2 分でした。参考として、A のボリュームの全読み取りの p50 は 1 MiB が 52.61 ms、5 MiB が 116.69 ms で、2026-10-10 のプール集計による 3 回の測定の区分の p50 は、1 MB が 50.07〜60.02 ms、5 MB が 118.60〜120.90 ms でした。サイズ、読み取り回数、ボリューム、ONTAP バージョンが異なるため、比較は主張しません。

### この比較の限界

- 1 つのファイルシステム、1 つのリージョン、2026-10-11 の約 46 分間（UTC の 08:38〜09:24）。オブジェクトサイズは 3 種類。同時実行数 1 の逐次読み取りで、VPC 外の 256 MB の Lambda からインターネットオリジンの S3 Access Points を読んでいます。
- 初回読み取りは、書き込みの完了から 6.5〜52.2 分後、データがキャパシティプールにあると初めて確認してから 8.1 分以上後に行いました。そのときの ONTAP のキャッシュの状態は不明です。確認したのはボリューム単位のキャパシティプールのサイズだけで、個々のオブジェクトの所在は確認していません。
- 1 回の呼び出しのサイズごとのオブジェクトは 10 個で、3 回の測定を通した条件・サイズごとのオブジェクトは 30 個です。有意性の検定はしておらず、3 回の測定では安定性は示せません。
- A1 と A2 は同じ構成で、最大 21.47 ms 違います（5 MiB の初回読み取り）。原因は不明です。
- 対象外: 第 2 世代やマルチ AZ のファイルシステム、他の ONTAP バージョン、同時実行数 2 以上、AUTO ポリシー、`default` 以外のクラウド取得ポリシー、VPC 内の Lambda、請求の比較。
- 規則の文面は、このリポジトリにない計画ファイルに、最初の呼び出しの前に書きました。
- boto3 と urllib3 のバージョン、および各呼び出しがコールドスタートかウォームかは記録していません。リクエスト料金もコストの数値も見積もっていません。

## スループットに影響する要因

### FSx スループットキャパシティ

FSx for ONTAP のスループットキャパシティは NFS、SMB、S3 AP アクセスで共有されます。本番ワークロードがスループットを消費している場合、S3 AP の読み取りは遅くなります。

| FSx スループットキャパシティ | S3 AP への影響 |
|------------------------|----------------------|
| 128 MB/s | 監査読み取りが本番と競合する可能性あり |
| 512 MB/s | 監査読み取りが本番に影響する可能性は低い |
| 2048 MB/s | 測定可能な影響なし |

### ネットワーク経路

| Lambda 配置 | S3 AP アクセス | レイテンシへの影響 |
|-----------------|-------------|----------------|
| VPC 外 | 直接（Internet-origin AP） | 最小レイテンシ |
| VPC 内 + NAT Gateway | NAT 経由 | リクエストあたり +10-30 ms |
| VPC 内 + Gateway EP のみ | タイムアウト（Internet-origin AP） | 動作しない |

### 同時実行

監査ポーラーは `ReservedConcurrentExecutions: 1` を使用して実行の重複を防止しています。これは各呼び出し内でファイルを逐次処理することを意味します。より高いスループットが必要な場合:
- Lambda メモリを増加（CPU 増加 = 処理高速化）
- 単一呼び出し内で `ThreadPoolExecutor` を使用して並列 GetObject
- SQS ベースのファンアウトで並列ファイル処理

### 階層化ポリシーとデータ階層

2026-10-10 に測った数値は、階層化ポリシーが AUTO のボリュームで、SSD（プライマリ階層）にあると推定されるデータを読んだ結果です。転記した値の階層化条件は、このページでは再掲していません。キャパシティプールへ階層化されたデータの読み取りは、2026-10-11 に一度だけ、「階層別の比較: SSD とキャパシティプール（2026-10-11）」で測りました。対象は 64 KiB・1 MiB・5 MiB のオブジェクト、同時実行数 1、1 つのファイルシステム、階層化ポリシーが NONE と ALL のボリュームです。この値を他のオブジェクトサイズ、同時実行数、階層化ポリシーに広げないでください。

## 推奨事項

### 一般的なデプロイ（< 100 ファイル/5 分）

デフォルト設定で十分です:
- `MAX_KEYS_PER_RUN=100`
- `SAFETY_THRESHOLD_MS=30000`
- Lambda メモリ: 256 MB
- Lambda タイムアウト: 300 秒

### 大量デプロイ（> 100 ファイル/5 分）

選択肢:
1. **スケジュール頻度を上げる**: `rate(5 minutes)` の代わりに `rate(1 minute)`
2. **Lambda メモリを増加**: 512 MB または 1024 MB で CPU 増強
3. **並列 GetObject**: ThreadPoolExecutor を使用（同時実行数 5-10）
4. **SQS ファンアウト**: 1 つの Lambda でファイル一覧取得、並列ワーカーで処理

### スループットの監視

パイプラインスループットを追跡するために以下の CloudWatch カスタムメトリクスを追加:

```python
import boto3

cloudwatch = boto3.client("cloudwatch")

cloudwatch.put_metric_data(
    Namespace="Custom/FSxONTAPPipeline",
    MetricData=[
        {
            "MetricName": "FilesProcessedPerInvocation",
            "Value": files_processed,
            "Unit": "Count",
        },
        {
            "MetricName": "ProcessingDurationMs",
            "Value": duration_ms,
            "Unit": "Milliseconds",
        },
        {
            "MetricName": "BytesReadPerInvocation",
            "Value": bytes_read,
            "Unit": "Bytes",
        },
    ],
)
```

## 自環境でのベンチマーク実行

ツールは [`benchmark/s3ap-throughput/`](../../benchmark/s3ap-throughput/README.md) にあります。構成は、`template.yaml`（CloudFormation スタック。メモリ 256 MB・タイムアウト 300 秒・VPC 設定なしの Lambda 1 つ）、`run-benchmark.sh`（呼び出しヘルパー）、`handler.py`（関数本体。単体テストは `tests/`）です。

```bash
# 1. Deploy the benchmark Lambda. Replace the placeholder with your
#    S3 Access Points ARN.
aws cloudformation deploy \
  --template-file benchmark/s3ap-throughput/template.yaml \
  --stack-name fsxn-s3ap-benchmark \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    S3AccessPointArn=<s3-access-point-arn> \
    BenchmarkRegion=ap-northeast-1

# 2. Run the ListObjectsV2 and GetObject tests. Every value comes from an
#    environment variable. S3AP accepts the alias or the ARN.
FUNCTION_NAME=fsxn-s3ap-benchmark-fn \
S3AP=<s3-access-point-alias-or-arn> \
PREFIX=<key-prefix>/ \
AWS_REGION=ap-northeast-1 \
  benchmark/s3ap-throughput/run-benchmark.sh

# 3. Remove the stack when the measurement is done.
aws cloudformation delete-stack --stack-name fsxn-s3ap-benchmark
```

`run-benchmark.sh` は 1 つの `PREFIX` を 2 つのテストの両方に使い、結合した JSON を 1 ファイル書き出します。任意の上書きは `LIST_ITERATIONS`（既定 20）、`GET_ITERATIONS`（既定 5）、`MAX_KEYS`（既定 10）、`BENCHMARK_RUN_ID`、`OUT_FILE` です。2026-10-10 の生データは、この結合ファイルではなく、関数のテストごとの応答で、サイズのプレフィックスごとに 1 ファイルです。

結果は環境の情報とあわせて記録してください。FSx for ONTAP のスループットキャパシティ、S3 Access Points のネットワークオリジン、リージョン、日付、実行 ID です。デプロイの詳細はツールの [README](../../benchmark/s3ap-throughput/README.md) にあります。
