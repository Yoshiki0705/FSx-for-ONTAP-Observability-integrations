# S3 Access Point 読み取りスループットベンチマーク

## 目的

本ドキュメントは、S3 Access Points 経由で Amazon FSx for NetApp ONTAP の監査ログを読み取る際のベンチマーク手法と参考結果を提供します。これらの結果は**サイジングの参考値であり、サービス上限ではありません**。

「本リポジトリでの実測（2026-10-10）」「プール集計による再測定（2026-10-10）」「階層別の比較: SSD とキャパシティプール（2026-10-11）」「階層化の経路: 直接 ALL と NONE から ALL への切り替え（2026-10-11）」の 4 つの節が、このリポジトリにある、S3 Access Points 読み取りレイテンシの唯一の測定です。生データは、1 つ目が `benchmark/s3ap-throughput/results/2026-10-10/`（平均方式）、2 つ目が `benchmark/s3ap-throughput/results/2026-10-10-pooled/`（プール集計）、3 つ目が `benchmark/s3ap-throughput/results/2026-10-11-tier/`（階層化ポリシーが NONE と ALL のボリューム、解析スクリプト付き）、4 つ目が `benchmark/s3ap-throughput/results/2026-10-11-tier-path/`（ALL に直接至ったボリュームと NONE からの切り替えで至ったボリューム、解析スクリプト付き）と `benchmark/s3ap-throughput/results/2026-10-11-tier-elapsed/`（経過時間を入れ替えて読んだ別の 2 ボリューム。3 つの実験の 8 ボリュームを比べる解析スクリプトも含む）にコミットしています。位置の確認は 2 つ目の節の中の小節群で、生データは `benchmark/s3ap-throughput/results/2026-10-10-position/` にコミットしています。「参考結果」の節の値は、姉妹リポジトリからの転記です。

## 測定方法

### テストスクリプト

下のスクリプトは測定方法の例示です。2026-10-10 の数値を出したのは `benchmark/s3ap-throughput/` に収録したツールの当時の版で、スクリプトとは、数値の読み方に関わる 2 点が違います。p50 と p99 を `statistics.median` と `int(iterations * 0.99)` の添字ではなく nearest-rank 法で求めること、オブジェクトごとの結果に加えてサイズ区分ごとの集計を返すことです。

```python
"""S3 AP throughput benchmark for FSx for ONTAP audit logs.

Run from Lambda or EC2 in the same region as the S3 Access Point.
"""

import time
import statistics
import boto3

s3 = boto3.client("s3")

S3_AP_ARN = "arn:aws:s3:ap-northeast-1:123456789012:accesspoint/fsxn-audit-ap"
PREFIX = "audit/svm-prod-01/2026/05/"


def benchmark_list_objects(iterations: int = 10) -> dict:
    """Measure ListObjectsV2 latency."""
    latencies = []
    for _ in range(iterations):
        start = time.perf_counter()
        s3.list_objects_v2(Bucket=S3_AP_ARN, Prefix=PREFIX, MaxKeys=100)
        latencies.append((time.perf_counter() - start) * 1000)
    return {
        "operation": "ListObjectsV2",
        "iterations": iterations,
        "p50_ms": statistics.median(latencies),
        "p99_ms": sorted(latencies)[int(iterations * 0.99)],
        "mean_ms": statistics.mean(latencies),
    }


def benchmark_get_object(keys: list[str], iterations: int = 5) -> dict:
    """Measure GetObject latency and throughput by object size."""
    results = []
    for key in keys:
        latencies = []
        sizes = []
        for _ in range(iterations):
            start = time.perf_counter()
            resp = s3.get_object(Bucket=S3_AP_ARN, Key=key)
            body = resp["Body"].read()
            latencies.append((time.perf_counter() - start) * 1000)
            sizes.append(len(body))
        avg_size = statistics.mean(sizes)
        avg_latency = statistics.mean(latencies)
        throughput_mbps = (avg_size / 1024 / 1024) / (avg_latency / 1000) if avg_latency > 0 else 0
        results.append({
            "key": key,
            "size_bytes": int(avg_size),
            "p50_ms": statistics.median(latencies),
            "p99_ms": sorted(latencies)[min(int(iterations * 0.99), iterations - 1)],
            "throughput_mbps": round(throughput_mbps, 2),
        })
    return results
```

### オブジェクトサイズカテゴリ

| カテゴリ | 一般的なサイズ | 説明 |
|----------|-------------|-------------|
| Small | 1-10 KB | 単一監査イベント（JSON） |
| Medium | 100 KB - 1 MB | ローテーション済み監査ログファイル（典型的） |
| Large | 1-5 MB | 高アクティビティ期間のログファイル |

## 本リポジトリでの実測（2026-10-10）

> **測定上の注意**: この節は先の 2026-10-10 の測定です。平均方式を使ったため、p99 は「プール集計による再測定（2026-10-10）」の p99（プールした 120 サンプルの nearest-rank 法の値）と比較できません。この節の区分の p99 は、オブジェクトごとの p99 3 個の平均で、オブジェクトごとの p99 は 10 サンプルのうち最大の値です。裾のレイテンシは、プール集計の節の値を参照し、参考値として読んでください。

根拠区分は `verified` で、対象は次の 1 文だけです。上記「テスト環境」で、2026-10-10 に、これらのレイテンシを観測しました。他のファイルシステム、同時実行数、ネットワーク経路、日付には及びません。測定は同じ日に約 20 分あけて 2 回取りました（生データの時刻は UTC の 08:09 と 08:29）。したがって数値は安定値ではなく、観測した幅を示します。

ボリュームの階層化ポリシーは AUTO、クーリング期間は 31 日で、テストオブジェクトは読み取りの数分前に書き込んでいます。このため、読み取りは SSD（プライマリ階層）から返されたと推定しています。これはポリシーとオブジェクトの経過時間からの推定で、実行中に階層別の容量メトリクスは取得していません。

### 集計方法

各オブジェクトを 10 回、順番に読みました（同時実行数 1）。ListObjectsV2 は 20 回呼び、MaxKeys は上書きしていないのでツールの既定値 100 が効いています。この測定を行った版のツールは、オブジェクトごとに nearest-rank 法の p50・p99 と平均を計算しました。下表のサイズ区分ごとの p50 と p99 は、3 個のオブジェクトそれぞれの p50 と p99 の単純平均です。プールした 30 サンプルのパーセンタイルではありません。後続の版のツールは、区分ごとの値をプールしたサンプルから計算し、各区分に `percentile_method: "pooled_nearest_rank"` を付けます（[#147](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/issues/147)）。`results/2026-10-10/` の生データにこのキーはありません。後述のプール集計による再測定は、このような版で取りました。そのため、後続の版が出す区分の値は、この節の表と直接は比較できません。オブジェクト 1 個のスループットはそのオブジェクトの平均レイテンシとサイズから求め、区分の値は 3 個の平均です。ここでの MB/s は、ツールと同じく MiB/s（サイズを 1,048,576 バイトで割った値）です。

### この測定の限界

- p99 は参考値にとどまります。オブジェクトごとの p99 は 10 サンプルの最大値で、ListObjectsV2 の p99 は 20 サンプルの最大値です。実行 2 の 5 MB 区分の p99（444.951 ms）は、3 個のオブジェクトの最大値（152.683、361.481、820.689 ms）の平均で、1 個のオブジェクトの 1 回の遅い読み取りが大半を決めています。生データは要約のみでイテレーションごとのサンプルを残していないため、遅いサンプルの原因は後から確認できません。
- 2 回の測定では統計的な安定性は示せません。分散、信頼区間、安定した p99 のいずれも主張しません。
- ListObjectsV2 の測定では、12 個のテストオブジェクトに加えて、既存の大きなファイル（約 103 MiB）が 1 個同じプレフィックスにあり、13 キーを列挙しました。GetObject の測定はサイズごとに別のプレフィックスを使ったため影響を受けていません。13 キーの列挙結果は、キー数がもっと多いディレクトリについては何も示しません。
- スループットは同時実行数 1 の 1 ストリームあたりの値で、平均レイテンシとオブジェクトサイズから求めています。ファイルシステムのスループット上限ではなく、並列読み取りについても何も示しません。1 KB の値は帯域ではなくリクエストのレイテンシを反映しています。
- ツールは Lambda のコールドスタートの影響を分けていません。最初の ListObjectsV2 のサンプルや各呼び出しの最初のリクエストには、接続の確立が含まれている可能性があります。保存した要約からは、最大値が最初の呼び出しだったかどうかは分かりません。
- 対象外: 同時実行数 2 以上、VPC 内の Lambda や NAT 経由の経路（後述「ネットワーク経路」のレイテンシ差はこの測定から導いたものではありません）、他の Lambda メモリサイズ、他のスループットキャパシティ、第 2 世代やマルチ HA ペアのファイルシステム、より大きなディレクトリ。
- この測定の対象外: 階層化ポリシーが ALL のボリューム、およびすでにキャパシティプールへ階層化されたデータ。これらは後の測定で、3 種類のオブジェクトサイズ、同時実行数 1、1 つのファイルシステムについて測定しました。「階層別の比較: SSD とキャパシティプール（2026-10-11）」を参照してください。この節の値はキャパシティプールの値ではありません。

## プール集計による再測定（2026-10-10）

根拠区分は `verified` で、対象は次の 1 文だけです。上記「テスト環境」で、2026-10-10 に、3 回の測定（UTC の 14:55〜14:59）でこれらのレイテンシを観測しました。先の測定（UTC の 08:09〜08:29）と同じ日の後の時間帯で、区分ごとの値をプールしたサンプルから計算する版のツールを使っています。他のファイルシステム、リージョン、同時実行数、ネットワーク経路、日付には及びません。表は、見出しに「導出値」とあるものを除き、ツールの出力そのままです。導出値は、コミットした生データから計算した値で、ツールの出力ではありません。これは 1 つの環境でのサンプル実行の結果で、サイジングの参考値です。本番環境の見積りでも、サービス上限でもありません。

### 環境と先の測定との差

ファイルシステム、ボリューム、リージョン、Lambda の設定は「テスト環境」と同じです（SINGLE_AZ_1、スループットキャパシティ 128 MBps、HA ペア 1 組、1024 GiB。クライアントは同じリージョンの VPC 外にある 256 MB の Lambda）。ボリュームの階層化ポリシーは AUTO、クーリング期間は 31 日で、測定の前後に読み取り、値は同一でした。SSD 上にあったことは、ポリシーとオブジェクトの経過時間からの推定で、階層別の容量メトリクスは取得していません。ONTAP のバージョンは、この再測定では再確認していません。先の測定との違いは次のとおりです。

| 項目 | 先の測定（平均方式） | プール集計による再測定 |
|------|---------------------|------------------------|
| ツールの版 | 区分ごとの値を、オブジェクトごとのパーセンタイルの平均で出す版 | `main` のコミット `6808382` のツール（[#147](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/issues/147)） |
| 測定回数 | 2 回、約 20 分間隔 | 3 回、約 4 分以内 |
| オブジェクトあたりの読み取り回数 | 10 | 40 |
| 区分あたりのサンプル数 | 30（ファイルには残していない） | 120（`samples_ms` として保存） |
| ListObjectsV2 | 20 回、13 キー | 120 回、12 キー |
| テストオブジェクト | ランダムバイト列。1 KB・100 KB・1 MB・5 MB を各 3 個、サイズごとに別のプレフィックス。ListObjectsV2 のプレフィックスには、既存の 103 MiB のファイルも 1 個あった | 同じ構成を新しいプレフィックスに置いた。プレフィックスにあったのはテストオブジェクト 12 個だけ |
| S3 Access Points | タイプは ONTAP、インターネットオリジン、UNIX ユーザー `root` | 同じタイプ。この再測定のために新規に作成し、終了後に削除 |

このため、2 回の ListObjectsV2 の値は厳密には比較できません（12 キーと 13 キー、120 回と 20 回）。

### プール集計とサンプル数

- 区分ごとの値は、3 個のオブジェクト × 40 回 = 1 回の測定あたり 120 サンプルをプールし、nearest-rank 法で求めた値です。各区分に `percentile_method: "pooled_nearest_rank"` と `sample_count: 120` が付きます。
- オブジェクトごとの生のレイテンシは `per_object[].samples_ms` に残っています（オブジェクトあたり 40 個）。
- ListObjectsV2 は、1 回の測定につき 120 回呼んだ 1 系列です。結果に生サンプルを残さないため、ファイルから p99 を再計算できません。
- 120 サンプルの nearest-rank 法の p99 は、2 番目に大きいサンプルです。
- 読み取りは単一ストリームで逐次に行いました（同時実行数 1）。スループットは 1 ストリームあたりの値で、ファイルシステムの上限ではありません。MB/s は MiB/s です。
- 合計は読み取り 1,800 回（ListObjectsV2 が 360 回、GetObject が 1,440 回）で、GetObject で読んだデータは約 2.1 GiB です。

## 階層別の比較: SSD とキャパシティプール（2026-10-11）

根拠区分: 測定値は、示した環境・日付・サンプル数について `verified` です。それ以外の主張は、「この節の主張の根拠区分」にそれぞれの区分を示します。これらのレイテンシと操作数は、下記「環境」の環境で、2026-10-11 に、UTC の 08:38〜09:24 の 27 回の測定呼び出しで観測しました。ツールは `main` のコミット `6808382` のものです。他のファイルシステム、リージョン、ONTAP バージョン、オブジェクトサイズ、同時実行数、ネットワーク経路、日付には及びません。これは 1 つの環境でのサンプル実行の結果で、サイジングの参考値です。本番環境の見積りでも、サービス上限でもありません。表は、見出しに「導出値」とあるものを除き、ツールの出力そのままです。導出値は、`benchmark/s3ap-throughput/results/2026-10-11-tier/` にコミットした生データから計算した値で、ツールの出力ではありません。

階層化ポリシーが ALL のボリューム（B）では、1 MiB と 5 MiB で、オブジェクトの初回読み取りが、階層化ポリシーが NONE の 2 つのボリューム（A1、A2）より、3 回の測定のすべてで長くかかりました。実行ごとの中央値の差 D は、1 MiB で +67.8〜+74.0 ms（A1 と A2 の差の最大 14.0 ms）、5 MiB で +150.8〜+167.1 ms（A1 と A2 の差の最大 21.5 ms）でした。64 KiB では差を確立できておらず、初回読み取りと反復読み取りをまとめた場合も、どのサイズでも確立できていません。B の呼び出しが起こしたキャパシティプールの読み取り操作は、1 MiB で 56、56、54 回、5 MiB で 332、323、298 回（オブジェクトあたり 5.4〜5.6 回と 29.8〜33.2 回）で、64 KiB では 0 回でした。これらはこの環境での結果で、サービスの一般的な特性ではありません。これは、階層化ポリシー ALL で作成し、そのポリシーの下でデータを直接書き込んだボリューム（B）の結果です。同じ日に同じファイルシステムで行った 2 つ目の実験では、データの書き込み後に NONE から ALL へ切り替えたボリュームの初回読み取りで、キャパシティプールの読み取りは見つかりませんでした。「階層化の経路: 直接 ALL と NONE から ALL への切り替え（2026-10-11）」を参照してください。

### 最初の呼び出しの前に固定した判定規則

サイズと読み取りクラスごとに、`m_A1(r)`、`m_A2(r)`、`m_B(r)` を測定 `r` の呼び出しの中央値とします。このとき:

- `D(r) = m_B(r) - (m_A1(r) + m_A2(r)) / 2`
- `N(r) = |m_A1(r) - m_A2(r)|`
- `N_largest` は、3 回の測定の `N(r)` のうち最大の値

そのサイズとクラスで B が遅いと言うのは、3 回の測定のすべてで `D(r) > 0` かつ `D(r) > N_largest` のときだけです。そうでなければ、差は確立できていません（`open`）。規則の対象は、初回読み取りのクラスと全読み取りのクラスです。反復読み取りは、規則なしで示します。規則は片側だけです。B のほうが速いかどうかは検定せず、そう主張することもしません。規則の文面は、このリポジトリにない計画ファイルに、最初の呼び出しの前に書きました。そのため、規則とデータの前後関係は、このリポジトリからは確認できません。

### 裏付けられる範囲と、裏付けられない範囲

この環境と 3 回の測定について、数値が裏付けるのは次のことです。

- 1 MiB と 5 MiB で、ALL のボリューム（B、階層化ポリシー ALL で作成）のオブジェクトの初回読み取りは、NONE のボリュームより中央値が高く、その差は 3 回とも A1 と A2 の差の最大より大きい。測定ごとの D は、1 MiB が +67.80〜+73.97 ms、5 MiB が +150.78〜+167.09 ms。3 回をまとめた初回読み取りの p50 は、1 MiB が A で 53.70 ms、B で 122.70 ms（+69.00 ms、2.3 倍）、5 MiB が A で 118.15 ms、B で 277.82 ms（+159.66 ms、2.4 倍）。
- キャパシティプールから読まれたバイト数は、1 回の呼び出しあたりオブジェクトのバイト数の約 1 パス分で、4 パス分ではない。これは、キャパシティプールに届くのが初回読み取りだけであることと整合する。
- B について、ボリューム別の `CapacityPoolReadOperations` は、どの測定でも、ノード別の `get` カウンタの増分と一致する。

数値が裏付けないのは次のことです。

- 64 KiB での差、およびどのサイズでも、初回読み取りと反復読み取りをまとめた場合の差。
- B の反復読み取りが SSD と同じ速さだという主張。9 つの測定×サイズのセルで、反復読み取りの D は -12.14〜+17.60 ms、A1 と A2 の差は 0.44〜16.89 ms で、規則はこのクラスを定義していません。3 回をまとめた反復読み取りの p50 の差は、1 MiB が +2.65 ms、5 MiB が +15.71 ms で、初回読み取りの +69.00 ms と +159.66 ms に対する値です。
- コストや請求の数値。
- 反復読み取りが速い理由、および 64 KiB の初回読み取りがキャパシティプールの読み取りを起こさなかった理由（`hypothesis`）。候補の 1 つは ONTAP 内のキャッシュです。検証しておらず、他の原因は除外していません。B のキャパシティプールのサイズは書き込んだ全量と等しいので、64 KiB のオブジェクトも階層化されていたと推測されます。

各オブジェクトを 1 回だけ読む読み手には、初回読み取りの値が対応します。全読み取りの値には、この読み手が行わない反復読み取りが含まれます。その読み手が読むオブジェクトがすでにキャパシティプールにあるかどうかは、ボリュームの階層化ポリシーと、書き込みから読み取りまでの時間に依存します。この測定では、その時間は B のボリュームで 8.5〜50.2 分でした（27 回すべての呼び出しでは 6.5〜52.2 分）。同じ日のさらに 2 つの実験では、K1 と S3p（B と同じく ALL で作成して直接書き込み）の初回読み取りにはキャパシティプールの読み取りがあり、NONE から ALL へ切り替えた 4 つのボリュームにはなく、ALL で作成して直接書き込んだもう 1 つのボリューム（DIR）にもありませんでしたが、それらの実験は理由を切り分けていません（「階層化の経路: 直接 ALL と NONE から ALL への切り替え（2026-10-11）」を参照）。参考として、A のボリュームの全読み取りの p50 は 1 MiB が 52.61 ms、5 MiB が 116.69 ms で、2026-10-10 のプール集計による 3 回の測定の区分の p50 は、1 MB が 50.07〜60.02 ms、5 MB が 118.60〜120.90 ms でした。サイズ、読み取り回数、ボリューム、ONTAP バージョンが異なるため、比較は主張しません。

## 階層化の経路: 直接 ALL と NONE から ALL への切り替え（2026-10-11）

根拠区分: 測定値は、示した環境・日付・サンプル数について `verified` です。それ以外の主張は、「階層化の経路に関する主張の根拠区分」にそれぞれの区分を示します。使う区分は `documented`、`verified`、`hypothesis`、`open` です。この節には、同じファイルシステムで 2026-10-11 に行った 2 つの実験があります。実験 2（階層化の経路の実験、5 ボリューム）は、下記「階層化の経路の実験の環境」の環境で、UTC の 12:09〜13:23 の 47 回の呼び出し（測定の呼び出し 34 回、階層化前の読み取りの呼び出し 8 回、ウォームアップの呼び出し 5 回）で観測しました。実験 3（経過時間を入れ替えて読んだ 2 ボリューム）は、UTC の 15:56〜16:28 の 6 回の呼び出し（測定の呼び出し 4 回、ウォームアップの呼び出し 2 回）で観測しました。その環境は「実験 3: 環境と日程」にあります。上の階層別の比較は実験 1 です。他のファイルシステム、リージョン、ONTAP バージョン、オブジェクトサイズ、同時実行数、ネットワーク経路、日付には及びません。これらは 1 つの環境でのサンプル実行の結果で、サイジングの参考値です。本番環境の見積りでも、サービス上限でもありません。表は、見出しに「導出値」とあるものを除き、ツールの出力そのままです。導出値は、`benchmark/s3ap-throughput/results/2026-10-11-tier-path/`（実験 2）と `benchmark/s3ap-throughput/results/2026-10-11-tier-elapsed/`（実験 3）にコミットした生データから計算した値で、ツールの出力ではありません。

階層化ポリシーを、データの書き込み後に NONE から ALL へ切り替えた 3 つのボリューム（S2、S3、S4）では、階層化後の初回読み取りが起こしたキャパシティプールの読み取り操作は 0 回でした。各ボリュームの 30 回の読み取りは記録されており（同じ窓の `DataReadOperations` はボリュームごとに 30）、約 30 分後と約 60 分後の再読み取り（事後）でも 0 回でした。階層化ポリシー ALL で作成して直接書き込んだ 2 つのボリューム（K1、S3p）では、初回読み取りがキャパシティプールの読み取りを起こしました。K1 は 1,896 操作、246,862,656 B（読んだオブジェクトの論理サイズに対して 0.971）、S3p は 374 操作、916,864 B（論理サイズに対して 0.014、階層化されたバイト数に対して 1.07 倍（事後）。S3p で階層化されたバイト数は、論理サイズの約 1/74）でした。K1 の再読み取りは、約 3 分後に 9 操作、約 8.4 分後、30 分後、60 分後は 0 操作でした。切り替え前に各オブジェクトを 32 回読んだ場合（S2、S3）も、まったく読まなかった場合（S4）も、同じ 0 でした。最初の 6 つのボリューム（階層別の比較の B、K1、S3p、S2、S3、S4）では、B、K1、S3p（直接書き込み）の初回読み取りはキャパシティプールに届き、S2、S3、S4（NONE から ALL へ切り替え）の初回読み取りは届きませんでした。実験 1 と 2 のどの比較も書き込みの経路だけを変えておらず、書き込みの経路は、5 つの設定上の因子のうち、この 6 つのボリュームを完全に分けた唯一のものでした。6 つ目の因子、データがキャパシティプールに入ってから最初の読み取りまでの時間も、CloudWatch のラベルを記録のとおりに扱うと、6 つのボリュームを完全に分けました。どちらも、結果を見たあとに、調べた因子を並べて見つけた分け方で、弱い根拠にとどまります（粗い目安であり、統計的検定ではありません。「ボリュームごとの因子」を参照）。これらは日付つきの記述で、最初の 6 つのボリュームについてのものです。実験 3 がそれを成り立たなくしました。

実験 3 は、2 つのボリュームを、経過時間を入れ替えて読みました。DIR は、B、K1、S3p と同じく ALL で作成して直接書き込んだボリュームで、データがキャパシティプールに入ってから 5.4〜6.5 分後と 14.4〜15.5 分後の初回読み取りが、キャパシティプールの読み取り操作を 0 回起こしました。SW は、S2、S3、S4 と同じく NONE から ALL へ切り替えたボリュームで、15.6〜16.7 分後と 30.6〜31.7 分後に 0 回でした（`verified`、この環境、この日）。8 つのボリュームのうち、初回読み取りが正だった 3 つはすべて直接書き込みで、なしだった 1 つ（DIR）も直接書き込みでした。したがって、書き込みの経路は、この記録では十分条件ではありません。必要条件かどうかは示されていません（直接書き込みが 4 ボリューム、切り替えが 4 ボリューム）。経過時間もこれらを分けません（補助の DIR のコホート 2 を使うので、事後の比較です）。DIR のコホート 2 の範囲（14.4〜15.5 分、なし）は、初回読み取りでキャパシティプールの読み取りがあった K1（13.6〜16.0）と S3p（13.5〜15.6）の範囲に入ります。キャパシティプールの読み取りがあった読み取りとなかった読み取りを分ける経過時間の閾値は記録になく、経過時間は、ここでは単独で十分な説明ではありません（`verified`。範囲は点ではなく境界です）。この記録は、書き込みの経路だけを原因とする見方を裏付けません。`hypothesis` が上限で、データはそれを弱めます。

3 つ目の候補は事後で、未検証です（`hypothesis`）。同じ実験の他のボリュームが、そのボリュームの階層化の書き込みがある最後のバケットから最初の読み取りまでの間に読んだバイト数です（「8 つのボリュームをまとめた値（導出値、事後）」）。これは 8 つのボリュームの観察で、制御した比較ではありません。データ量、並列で書き込んだボリューム数（3、5、2）、実験の違いも制御していません。これらはこの環境での結果で、サービスの一般的な特性ではありません。

上の階層別の比較（実験 1）は、ALL で作成して直接書き込んだボリューム B を使いました。実験 2 は、データの書き込み後にポリシーを ALL へ切り替えた場合を加え、実験 3 は、直接書き込みのボリュームと切り替えたボリュームを、経過時間を入れ替えて読みます。

### 問い、設計、階層別の比較との差

実験 2 の問い: 階層化後のオブジェクトの初回読み取りがキャパシティプールに届くかどうかは、ALL で作成して直接書き込んだボリュームと、書き込み後に ALL へ切り替えたボリュームの間で異なるか。課金、他のオブジェクトサイズ、同時実行数 2 以上、第 2 世代やマルチ AZ のファイルシステム、他の ONTAP バージョンは対象外です。設計には、書き込みの経路だけを変える比較が含まれないことが分かったため（下の「ボリュームごとの因子」を参照）、結果は 2 つのボリューム群の間の分かれ方を記述するもので、その原因を書き込みの経路には帰しません。

AWS は、すでにデータがあるボリュームに ALL ポリシーを適用すると、既存のデータが SSD からキャパシティプールへ階層化されると記載しています（[ボリュームのストレージ容量](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/volume-storage-capacity.html)、階層化ポリシー、`documented`）。そのページには、そのデータの後の読み取りが、ALL の下で書いたデータの読み取りと同じようにキャパシティプールに届くかどうかは書かれていません。この実験が測るのはそこです。

1 つの SVM に 5 つのボリューム、条件ごとに 1 つ。S3p は S3 と同じ内容で、ALL で作成しました。

| ボリューム | ALL に至った経路 | 内容 | 階層化前の各オブジェクトの読み取り回数 | 階層化後に読むオブジェクト | 階層化後の読み取り |
|--------|--------------------|---------|-------------------------------------|----------------------------|---------------------|
| K1 | ALL で作成、データを直接書き込み | ランダムバイト列 | なし | 120（4 コホート × 3 サイズ × 10） | 12 個のプレフィックスすべての初回読み取り。コホート 1〜4 をそれぞれ 1 回ずつ、順に約 3 分、8.4 分、30 分、60 分後に再読み取り |
| S2 | NONE で作成、書き込み後に ALL へ切り替え | ランダムバイト列 | 32 | 30（3 サイズ × 10） | 初回読み取り。約 30 分後と約 60 分後に再読み取り（事後） |
| S3 | NONE で作成、書き込み後に ALL へ切り替え | 同一バイト | 32 | 30 | S2 と同じ |
| S3p | ALL で作成、データを直接書き込み | 同一バイト | なし | 30 | 初回読み取りのみ |
| S4 | NONE で作成、書き込み後に ALL へ切り替え | ランダムバイト列 | なし | 30 | S2 と同じ |

- サイズは 64 KiB、1 MiB、5 MiB で、サイズごとに 10 個のオブジェクト（K1 は 4 つのコホートそれぞれにサイズごと 10 個）。ランダムバイト列は `os.urandom` の出力で、ボリュームごと・オブジェクトごとに異なります。同一バイトの内容は 1 つのバイト値（文字 `r`）の繰り返しで、同じサイズのオブジェクトはすべて同一の内容です。各ボリュームには `warm/` の 64 KiB のオブジェクトが 1 個あり、ウォームアップの呼び出しで 4 回読みます。
- 階層化後は、1 回の呼び出しが各オブジェクトを 1 回ずつ読みます（`iterations` 1）。S2 と S3 は、切り替え前に SSD 上（ポリシー NONE）でオブジェクトごとに 32 回読んでいます。切り替えから階層化後の初回読み取りまでの間に読んだオブジェクトはありません。
- S2、S3、S4、S3p の初回読み取りは、ボリュームごとに 1 回の呼び出しです（`cold/`、`max_keys` 30、`iterations` 1: ListObjectsV2 が 1 回、GetObject が 30 回）。その中で、オブジェクトはキーの順に読みます。1 MiB の 10 個、5 MiB の 10 個、64 KiB の 10 個の順です。K1 の初回読み取りは 12 回の呼び出し（`c<cohort>/<size>/`、`max_keys` 10、`iterations` 1: 各 11 リクエスト）で、コホートごとに 64 KiB、1 MiB、5 MiB の順に行います。階層化前の読み取りは 8 回の呼び出し（`cold/`、`max_keys` 30、`iterations` 8: 各 241 リクエスト。S2 と S3 を交互に、r1 から r4）で、各オブジェクトを 32 回読みます。同時実行数は 1 で、呼び出しごとに新しい boto3 クライアントを使います。
- 設計で、1 つの因子だけが異なる比較は 2 つです。S2 と S4（階層化前の読み取り）、S2 と S3（内容、切り替えの経路）。書き込みの経路（ボリュームが ALL に至った経路）だけを変える比較はありません。K1 と S4 は、データ量（120 個に対して 30 個）と最初の読み取りまでの経過時間（「最初の読み取りまでの経過時間（導出値）」を参照）も異なります。S3p と S3 は、階層化前の読み取りも異なります。K1 と S3p は、内容とデータ量（120 個に対して 30 個）が異なります。

- 群の中のばらつきは異なります。直接書き込みのボリュームの測定したオブジェクト数は 90 個、120 個、30 個、切り替えたボリュームは 30 個、30 個、30 個で、30 個は両方の群に現れますが、そろっているのは切り替えた群だけです。ストレージ効率化が有効なのは B だけで、B は別の実験である階層別の比較で測定しました。他の 5 つのボリュームはこの実験で、ストレージ効率化を無効にして測定しました。そのため効率化のフラグは 2 つの群を分けず、直接書き込みの群は 2 つの実験にまたがり、切り替えた群は 1 つの実験に収まります。初回読み取りの単位も異なります。B は 1 回の呼び出しで 1 サイズ 10 個を読み、K1 は 10 個ずつ 12 回の呼び出し（UTC の 12:22:38.2〜12:23:01.9）で読み、S3p、S2、S3、S4 は 1 回の呼び出しで 30 個を読みました。
- 6 つ目の因子、データがキャパシティプールに入ってから最初の読み取りまでの時間は、ボリュームごとの範囲です（最後の列）。CloudWatch のラベルを記録のとおりに扱うと、これも 6 つのボリュームを完全に分けました。S2、S3、S4 は 7.4 分以下、B は 8.0 分以上、K1 と S3p は 13.5 分以上です。書き込みの経路の分け方と同じく、これも結果を見たあとに、調べた因子の中で見つけた分け方です（粗い目安で、統計的検定ではありません）。実験 3 がそれを成り立たなくしました。DIR のコホート 2（14.4〜15.5 分、なし）は、K1 と S3p（13.6〜16.0 分と 13.5〜15.6 分、キャパシティプールの読み取りあり）の範囲に入ります。「最初の読み取りまでの経過時間（導出値）」を参照してください。

この発見に至った経緯。書き込みの経路は、最初の呼び出しの前に固定した計画で、階層化前の読み取り、内容とともに候補の因子の 1 つでした。K1 と S4、S3p と S3 は、その因子のために計画した比較です（「最初の呼び出しの前に固定した解釈と、事後の 2 つの追加」を参照）が、どちらも因子を単独にはしません。上の表は、別の実験の B を加え、S3p を操作数と g（事後）で直接書き込みのボリュームの側に置いたもので、結果を見たあとに 6 つのボリュームの因子を並べて作りました。5 つの設定上の因子のうち書き込みの経路だけが 2 つの群を完全に分けたこと、および経過時間も 2 つの群を分けたことは、実験が検証した予測ではなく、実験の後で見つけた分け方でした。この種の発見がどの程度の重みを持つかの粗い目安として、6 つのボリュームを 3 つずつの 2 群に分ける分け方は 10 通りあるので、3 つのボリュームで一方の値、残りの 3 つで他方の値を取る 2 値の因子が、観測した分け方に偶然合う確率は 0.1 です。そのような独立な因子を 3 つ調べると、どれかが合う確率は約 0.27、6 つでは約 0.47 です。これは仮定つきの算術で、統計的検定ではなく、ここで調べた因子（書き込みの経路、内容、階層化前の読み取り、データ量、ストレージ効率化、経過時間）だけを数えています。調べていない因子（接続の状態、時刻、Lambda のコンテナの状態など）が 2 つの群を分けている可能性も残ります。実験 3 は、これらの分け方が見つかったあとに計画しました。DIR と SW を加えると、どちらの分け方も成り立ちませんでした。

### 最初の呼び出しの前に固定した解釈と、事後の 2 つの追加

最初の呼び出しの前に、このリポジトリにない計画ファイルに固定したもの。そのため、前後関係はこのリポジトリからは確認できません。

- 指標 f（キャパシティプール読み取り比）: 呼び出しの窓でのボリュームの `CapacityPoolReadBytes` を、その呼び出しが読んだオブジェクトの論理サイズで割った値。f が 0.10 未満なら「読み取りがキャパシティプールに届いていない」、0.80 超なら「ほぼ全量がキャパシティプールから読まれた」、その間は部分的として、値をそのまま報告する。
- 窓の規則: 呼び出しの開始した分から、終了した分の次の分までの、1 分ごとのバケット。
- K1 の再読み取りの間隔（約 3 分、8.4 分、30 分、60 分）。同じ f で読む。

同じ計画ファイルに、その後 2 つの追加を書きました。それぞれ、値が現れる箇所に事後と明記しています。K1 の約 3 分後、8.4 分後、30 分後、60 分後の再読み取りは、最初の呼び出しの前に固定していたので、事後とは明記していません。

2 つの追記の時刻は UTC の 12:36 と 12:42 です。初回読み取りは 12:23 までに行われ、約 30 分後の再読み取りは 12:52 に始まったので、2 つの追記はその間にあります。この前後関係は計画ファイルの記述で、このリポジトリからは確認できません。

計画ファイルになく、結果を見たあとに行ったもの: B を加えた表「ボリュームごとの因子」、6 つのボリュームの 2 つの群への分け方、5 つの設定上の因子のうち書き込みの経路だけが 2 つの群を完全に分けたという発見、経過時間の範囲。これらは事後で、発見がどこまで及ぶかは「ボリュームごとの因子」に示します。実験 3 には、最初の呼び出しの前に固定した独自の表があります（「実験 3: 問い、設計、最初の呼び出しの前に固定した解釈」）。その事後の部分もそこに挙げています。

### 最初の読み取りまでの経過時間（導出値）

経過時間は、データがキャパシティプールに入ってから、測定対象のオブジェクトを最初に読むまでの時間です。ボリュームによって異なり、オブジェクトがキャパシティプールに入った時刻は記録していないため、範囲として示します。各ボリュームの範囲は、そのボリュームの生データのディレクトリにある `analyze_capacity_pool.py` が、コミットしたファイルから計算します。この実験のディレクトリのものが K1、S3p、S2、S3、S4 を、階層別の比較のディレクトリのものが B を計算します。すべてのボリュームに同じ 1 つの規則を、`CapacityPoolWriteOperations` が 0 を超える 1 分ごとのバケット（`cw-all.tsv`。B は `cw-b-tiering.tsv` も）に適用します。「以上」の分は切り捨て、「以下」の分は切り上げて、どちらも境界として成り立つようにしています。

- 以上（下限）: 最後のバケットの終わりから、最初の読み取りの開始まで。データは、そのバケットの終わりまでにキャパシティプールに入っています。
- 以下（上限）: 最初のバケットの開始から、最初の読み取りの開始まで。バケットのラベルが、記録している書き込みより後でなければ、データはそのバケットより前にはキャパシティプールに入っていません。生データの README には、CloudWatch が、分の後半に走った呼び出しの操作を次の分のラベルにすることがあると書いています（読み取り操作で確認。書き込み操作では調べていません）。そのため、各「以下」は最大で約 1 分大きい可能性があります。K1 は 17.0、S3p は 16.6、S2 は 8.3、S3 と S4 は 8.4 までです。
- バケットは、ノードのカウンタが示す範囲では、この 5 つのボリュームについて欠けていません。`cw-all.tsv` の書き込み操作 120 回は、UTC の 09:24:08〜13:26:13 の間のノード 1 の `object_store_client_op` の `put` 行の増加分と等しく（「セットアップの確認（導出値）」を参照）、ファイルに欠けた書き込み操作があることを示す徴候はありません。
- 実行ログの時刻は境界に使いません。S2、S3、S4 の階層化の書き込み操作 15 回は、それぞれすべて 12:15 のバケットにあり、このバケットは切り替え要求の 1.6 分後、Amazon FSx API が ALL を初めて示した観測の 0.5 分後に始まります（観測はポーリングによるもので、ポリシーはそれより前に適用されていた可能性があります）。切り替え要求から数えた最初の読み取りまでの間隔は 8.9 分、9.0 分、9.0 分（534.1 秒、538.2 秒、540.5 秒）で、バケットに基づく「以下」より緩い値です。

- B には下限しかないため、B の読み取りから時間の閾値を位置づけることはできません。B の 64 KiB の読み取りは、階層化から 8.0 分以上、25.7 分以上、43.7 分以上後（実行 1〜3）にキャパシティプールの読み取りがなく、B の 1 MiB と 5 MiB の読み取りは、階層化から 11.0 分以上後以降にありました。64 KiB の 3 回の 0 は、いずれも時間の閾値に対して位置づけられず、この記録では経過時間では説明できません。K1 と S3p にはサイズ別の操作数がありません。経過時間と書き込みの経路が 6 つのボリュームで重なっていることは、計画しておらず、検証もしていません。
- S2、S3、S4 の約 30 分後と約 60 分後の再読み取り（データがキャパシティプールに入ってから 36 分以上後と 66 分以上後）は、約 7 分後にすでに 1 回読んだオブジェクトを読んでいるため、最初の読み取りに対する経過時間の検証になりません。K1 のコホートの再読み取り（約 3 分後に 9 操作、約 8.4 分後以降は 0）も同じです。実験 1 と 2 には、切り替えたボリュームで未読のオブジェクトを、データがキャパシティプールに入ってから 7.4 分より後（上の許容を入れて 8.4 分より後）に初めて読んだものも、直接書き込みのボリュームで 8.0 分未満の時点に初めて読んだものもありませんでした。実験 3 がその両方を与えます（最後の項目）。
- 実験 3 は、欠けていた両方の場合を与えます（「実験 3: 読み取り、階層化時の書き込み、ノードのカウンタ（導出値）」）。直接書き込みの DIR は、5.4〜6.5 分後（コホート 1）と 14.4〜15.5 分後（コホート 2）にキャパシティプールの読み取りがなく、NONE から切り替えた SW も、15.6〜16.7 分後（コホート 1）と 30.6〜31.7 分後（コホート 2）になしでした。DIR のコホート 2 の範囲は、初回読み取りでキャパシティプールの読み取りがあった K1（13.6〜16.0）と S3p（13.5〜15.6）の範囲に入ります。したがって、キャパシティプールの読み取りがあった初回読み取りとなかった初回読み取りを分ける経過時間の閾値は記録になく、経過時間は、この記録では単独で十分な説明ではありません（`verified`、この環境）。範囲は点ではなく境界です。DIR のコホート 2 は、同じボリュームのコホート 1 のあとに読んでおり、計画では先に読んだ影響を受けうるとしていました。DIR のコホート 2 のこの使い方は事後です。経過時間が他の因子と合わせて役割を持つかどうかは `open` です。

### 実験 3: 問い、設計、最初の呼び出しの前に固定した解釈

問い: 実験 1 と 2 では、ボリュームが ALL に至った経路（直接書き込み、または NONE からの切り替え）と、最初の読み取りまでの経過時間が一緒に変わっていました。直接書き込みのボリュームは、データがキャパシティプールに入ってから 13.5 分以上後（B は 8.0 分以上後）に最初に読まれ、切り替えたボリュームは 6.2〜7.4 分後でした。実験 3 はこの 2 つを入れ替えます。直接書き込みのボリュームを、切り替えたボリュームの経過時間（約 7 分）で読み、切り替えたボリュームを、直接書き込みのボリュームの経過時間（約 16 分）で読みます。この実験は、実験 1 と 2 の分け方が見つかったあとに計画しました（「ボリュームごとの因子」を参照）。課金、他のオブジェクトサイズ、同時実行数 2 以上、他のファイルシステム、他の ONTAP バージョンは対象外です。

実験 1 と 2 のファイルシステムの 1 つの SVM に 2 つのボリューム、条件ごとに 1 つ。

| ボリューム | ALL に至った経路 | 内容 | 測定したオブジェクト数 / ボリューム上のオブジェクト数（論理サイズ） | ストレージ効率化 | 階層化前の各オブジェクトの読み取り回数 | 階層化後の読み取り |
|--------|--------------------|---------|--------------------------------------------------|--------------------|------------------------------------|---------------------|
| DIR | ALL で作成、データを直接書き込み | ランダムバイト列 | 60 / 61（127,205,376 B） | 無効（作成時に指定、読み戻していない） | なし | コホート 1（30 個）、続けてコホート 2（別の 30 個）。それぞれ 1 回の呼び出し |
| SW | NONE で作成、書き込み後に ALL へ切り替え | ランダムバイト列 | 60 / 61（127,205,376 B） | 無効（作成時に指定、読み戻していない） | なし | コホート 1（30 個）、続けてコホート 2（別の 30 個）。それぞれ 1 回の呼び出し |

- 2 つのボリュームでそろえたもの: ファイルシステムと SVM、ボリュームのサイズ（1024 MiB）、UNIX セキュリティスタイル、スナップショットポリシーなし、指定したストレージ効率化のフラグ、内容の種類（`os.urandom` のランダムバイト列で、ボリュームごと・オブジェクトごとに異なる）、データ量（127,205,376 B）、オブジェクトのサイズと個数、階層化前の読み取りなし（ウォームアップを除く）、読み取りの手順。各ボリュームには `warm/` の 64 KiB のオブジェクトが 1 個あり、ウォームアップの呼び出しで 4 回読みます。`cold/c1/` と `cold/c2/` には、それぞれ 64 KiB、1 MiB、5 MiB を 10 個ずつ置きます。
- そろえていないもの: ALL に至った経路と、設計上の読み取りまでの経過時間（DIR のコホートは書き込みの終了から約 7 分後と約 16 分後、SW のコホートは階層化から約 16 分後と約 31 分後）。計画しておらず異なるもの: 最初の読み取りの前にもう一方のボリュームが行った読み取り（「8 つのボリュームをまとめた値（導出値、事後）」）、およびデータがキャパシティプールに入った時刻（DIR は 15:56 の分、SW は 15:57 の分）。2 つのボリュームの書き込みは並列で行いました。
- コホートの読み取りは、それぞれ 1 回の呼び出しです（`cold/c1/` または `cold/c2/`、`max_keys` 30、`iterations` 1: ListObjectsV2 が 1 回、GetObject が 30 回）。その中で、オブジェクトはキーの順に読みます。1 MiB の 10 個、5 MiB の 10 個、64 KiB の 10 個の順です。同時実行数は 1 で、呼び出しごとに新しい boto3 クライアントを使います。各ボリュームのコホート 1 が主な読み取りです。コホート 2 は補助で、同じボリュームのコホート 1 のあとに読むため、計画では先に読んだ影響を受けうるとしています。影響の有無と大きさは分かりません。
- 実験 2 との違い: ボリュームは 5 つでなく 2 つ。データ量は各ボリュームで 127,205,376 B（実験 2 は 63,635,456 B、K1 は 254,345,216 B）。階層化前の読み取りなし。切り替えたボリュームを、約 7 分でなく約 16 分後に初めて読む。

最初の呼び出しの前に、このリポジトリにない計画ファイルに固定したもの。そのため、前後関係はこのリポジトリからは確認できません（計画ファイルの凍結は UTC の 15:45:11 で、ボリュームの作成は 15:45:39 であり、後者は `run-log-times.tsv` にあります）。

- 指標 f（キャパシティプール読み取り比）と窓の規則は、実験 1 と 2 と同じです（「最初の呼び出しの前に固定した解釈と、事後の 2 つの追加」を参照）。f が 0.10 未満なら「読み取りがキャパシティプールに届いていない」、0.80 超なら「ほぼ全量がキャパシティプールから読まれた」、その間は部分的として、値をそのまま報告する。
- 主な 2 つの読み取り（各ボリュームのコホート 1）の読み方:

| SW コホート 1（約 16 分後） | DIR コホート 1（約 7 分後） | 事前に固定した読み方 |
|----------------------------|----------------------------|--------------------------|
| 0.10 未満 | 0.80 超 | この範囲の経過時間では分かれ方を説明できない。書き込みの経路、またはそれと結びついた因子が残る。書き込みの経路の `hypothesis` を強める |
| 0.80 超 | 0.10 未満 | 経過時間で分かれ方を説明できる。書き込みの経路は要らない |

- 階層化時の書き込み比: `CapacityPoolWriteBytes` を論理サイズで割った値。ランダムな内容では実験 1 と 2 で約 0.998。外れた場合は、あとでその理由を説明する。

- 停止条件: ボリュームと S3 Access Points が 15 分以内に利用可能にならない、一覧取得がマニフェストと食い違う、DIR のキャパシティプール階層が最初の読み取りの前に論理サイズの 95 % に届かない、SW のそれが切り替え要求から 60 分以内に 95 % に届かない。いずれにも当たりませんでした。

### 実験 3: 読み取り、階層化時の書き込み、ノードのカウンタ（導出値）

コホートの読み取りのそれぞれに、開始した分から終了した分の次の分までの CloudWatch の 1 分ごとのバケットを割り当てました。実験 1 と 2 と同じ規則です。30 オブジェクトの 1 回の呼び出しが読むのは 63,569,920 B で、f は、窓でのキャパシティプールの読み取りバイト数をこの値で割った値です。経過時間は、階層化の書き込みがある最後の 1 分ごとのバケットの終わりと、最初のバケットの開始から、読み取りの開始までの範囲で、「最初の読み取りまでの経過時間（導出値）」の規則によります。

|------|--------|-------------|------------------------------------------------------------------------:|------------------------------:|-------------------------:|--:|---------------------:|
| コホート 1（主） | DIR | 16:02:26 | 5.4〜6.5 | 0 | 0 | 0.000 | 30 |
| コホート 2（補助） | DIR | 16:11:26 | 14.4〜15.5 | 0 | 0 | 0.000 | 30 |

| コホート 2（補助） | SW | 16:28:36 | 30.6〜31.7 | 0 | 0 | 0.000 | 30 |

- 最初の呼び出しの前に固定した表の行: 主な 2 つの読み取りはどちらも 0.10 未満で、4 行目です。その行によれば、直接書き込みのボリュームが約 7 分で 0 なら直接の経路にもキャパシティプールの読み取りが現れるまでの時間があり、切り替えたボリュームが約 16 分で 0 なら切り替えの経路は 16 分より長く要ります。経過時間だけでは、2 つの群の分かれ方を説明できません。この読み方のうち、切り替えの側は成り立ちます（SW は 31.7 分まで 0 でした）。直接の側は裏付けられません（補助のコホート 2 を使うので、事後です）。DIR のコホート 2 は 14.4〜15.5 分で 0 であり、次の項目の K1 と S3p の範囲の内側にあるので、直接書き込みのボリュームから「読み取りが現れるまでの時間」は読み取れません。
- DIR のコホート 2（補助なので、事前に固定した読み方の外）は、直接書き込みのボリュームで、14.4〜15.5 分で 0 でした。実験 2 の K1 と S3p も直接書き込みで、13.6〜16.0 分と 13.5〜15.6 分でキャパシティプールの読み取りがありました。この比較は事後です。「8 つのボリュームをまとめた値（導出値、事後）」を参照してください。

### 実験 3: 逸脱と限界

計画からの逸脱:

- 1 つのファイルシステム、1 つのリージョン、2026-10-11 のみ（呼び出しは UTC の 12:09〜13:23。ボリュームの作成は実行ログによる 12:03:50 頃、最後のノードカウンターの読み取りは 13:26:13）。オブジェクトサイズは 3 種類。同時実行数 1 の逐次読み取りで、VPC 外の 256 MB の Lambda からインターネットオリジンの S3 Access Points を読んでいます。
- 条件ごとに 1 つのボリューム、ボリュームあたり 30 オブジェクト（K1 は 120）。有意性の検定はなく、n はサイズごと・読み取りごとに 10 です。
- 実験 1 と 2 には、書き込みの経路だけを変える比較はありません。K1 と S4 は、データ量（120 個に対して 30 個）と最初の読み取りまでの経過時間（13.6〜16.0 分に対して 6.3〜7.4 分）が異なります。S2、S3、S4 の約 30 分後と約 60 分後の再読み取り（事後）も 0 でしたが、約 7 分後にすでに読んだオブジェクトの再読み取りなので、経過時間が差を説明するかどうかの検証にはなりません。設計では経過時間を変えていません。実験 3 では DIR と SW が最も近い組ですが、読み取りの経過時間ともう一方のボリュームの読み取りが異なります（「実験 3: 逸脱と限界」）。
- 切り替え前の読み取り回数は 32 回の 1 通り、切り替え要求から最初の読み取りまでの間隔は 534〜541 秒の 1 通りです。どちらも振っていません。
- 指定した以外のボリュームの設定は読み戻していません。ストレージ効率化、クラウド取得ポリシー、Amazon FSx API が返した以外の階層化ポリシーです。
- K1 と S3p のサイズ別の操作数は得られていません。0 は、Sum が正のデータポイントがないことを意味します。
- 解釈の文面は、このリポジトリにない計画ファイルに、最初の呼び出しの前に書きました。
- boto3 と urllib3 のバージョン、各呼び出しがコールドスタートかウォームか、およびデプロイしたツールのコミットは記録していません。リクエスト料金もコストの数値も見積もっていません。
- ノード別カウンタの区間は、この実験の直前ではなく、階層別の比較の最後のカウンタの読み取りから始まります。
- 計画からの逸脱:
  - S2、S3、S4 の初回読み取りは、切り替え要求の 503 秒後ではなく 534〜541 秒後に始まりました。ポーリング出力の表示の誤りで、開始が約 30 秒遅れました。
  - S4 の繰り返しの更新要求は、更新の進行中として拒否されました。影響はありません。
  - 分析用の取得で重複した行があり、一時的に操作数が 2 倍に見えました。重複の除去で直し、`DataReadOperations` はウィンドウごとに 30 に戻りました。

## スループットに影響する要因

### FSx スループットキャパシティ

FSx for ONTAP のスループットキャパシティは NFS、SMB、S3 AP アクセスで共有されます。本番ワークロードがスループットを消費している場合、S3 AP の読み取りは遅くなります。

| FSx スループットキャパシティ | S3 AP への影響 |
|------------------------|----------------------|
| 128 MB/s | 監査読み取りが本番と競合する可能性あり |
| 512 MB/s | 監査読み取りが本番に影響する可能性は低い |
| 2048 MB/s | 測定可能な影響なし |

### ネットワーク経路

| Lambda 配置 | S3 AP アクセス | レイテンシへの影響 |
|-----------------|-------------|----------------|
| VPC 外 | 直接（Internet-origin AP） | 最小レイテンシ |
| VPC 内 + NAT Gateway | NAT 経由 | リクエストあたり +10-30 ms |
| VPC 内 + Gateway EP のみ | タイムアウト（Internet-origin AP） | 動作しない |

### 同時実行

監査ポーラーは `ReservedConcurrentExecutions: 1` を使用して実行の重複を防止しています。これは各呼び出し内でファイルを逐次処理することを意味します。より高いスループットが必要な場合:
- Lambda メモリを増加（CPU 増加 = 処理高速化）
- 単一呼び出し内で `ThreadPoolExecutor` を使用して並列 GetObject
- SQS ベースのファンアウトで並列ファイル処理

### 階層化ポリシーとデータ階層

2026-10-10 に測った数値は、階層化ポリシーが AUTO のボリュームで、SSD（プライマリ階層）にあると推定されるデータを読んだ結果です。転記した値の階層化条件は、このページでは再掲していません。キャパシティプールへ階層化されたデータの読み取りは、2026-10-11 に 1 つのファイルシステムで行った 3 つの実験、「階層別の比較: SSD とキャパシティプール（2026-10-11）」と、「階層化の経路: 直接 ALL と NONE から ALL への切り替え（2026-10-11）」の 2 つの実験で測りました。対象は 64 KiB・1 MiB・5 MiB のオブジェクト、同時実行数 1、階層化ポリシーが NONE と ALL のボリューム、および ALL に直接至ったボリュームと NONE からの切り替えで至ったボリュームです。この値を他のオブジェクトサイズ、同時実行数、階層化ポリシーに広げないでください。

## 推奨事項

### 一般的なデプロイ（< 100 ファイル/5 分）

デフォルト設定で十分です:
- `MAX_KEYS_PER_RUN=100`
- `SAFETY_THRESHOLD_MS=30000`
- Lambda メモリ: 256 MB
- Lambda タイムアウト: 300 秒

### 大量デプロイ（> 100 ファイル/5 分）

選択肢:
1. **スケジュール頻度を上げる**: `rate(5 minutes)` の代わりに `rate(1 minute)`
2. **Lambda メモリを増加**: 512 MB または 1024 MB で CPU 増強
3. **並列 GetObject**: ThreadPoolExecutor を使用（同時実行数 5-10）
4. **SQS ファンアウト**: 1 つの Lambda でファイル一覧取得、並列ワーカーで処理

### スループットの監視

パイプラインスループットを追跡するために以下の CloudWatch カスタムメトリクスを追加:

```python
import boto3

cloudwatch = boto3.client("cloudwatch")

cloudwatch.put_metric_data(
    Namespace="Custom/FSxONTAPPipeline",
    MetricData=[
        {
            "MetricName": "FilesProcessedPerInvocation",

        },
```

## 自環境でのベンチマーク実行

ツールは [`benchmark/s3ap-throughput/`](../../benchmark/s3ap-throughput/README.md) にあります。構成は、`template.yaml`（CloudFormation スタック。メモリ 256 MB・タイムアウト 300 秒・VPC 設定なしの Lambda 1 つ）、`run-benchmark.sh`（呼び出しヘルパー）、`handler.py`（関数本体。単体テストは `tests/`）です。

```bash
# 1. Deploy the benchmark Lambda. Replace the placeholder with your
#    S3 Access Points ARN.
aws cloudformation deploy \
  --template-file benchmark/s3ap-throughput/template.yaml \
  --stack-name fsxn-s3ap-benchmark \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    S3AccessPointArn=<s3-access-point-arn> \
    BenchmarkRegion=ap-northeast-1

# 2. Run the ListObjectsV2 and GetObject tests. Every value comes from an
#    environment variable. S3AP accepts the alias or the ARN.
FUNCTION_NAME=fsxn-s3ap-benchmark-fn \
S3AP=<s3-access-point-alias-or-arn> \
PREFIX=<key-prefix>/ \
AWS_REGION=ap-northeast-1 \
  benchmark/s3ap-throughput/run-benchmark.sh

# 3. Remove the stack when the measurement is done.
aws cloudformation delete-stack --stack-name fsxn-s3ap-benchmark
```

`run-benchmark.sh` は 1 つの `PREFIX` を 2 つのテストの両方に使い、結合した JSON を 1 ファイル書き出します。任意の上書きは `LIST_ITERATIONS`（既定 20）、`GET_ITERATIONS`（既定 5）、`MAX_KEYS`（既定 10）、`BENCHMARK_RUN_ID`、`OUT_FILE` です。2026-10-10 の生データは、この結合ファイルではなく、関数のテストごとの応答で、サイズのプレフィックスごとに 1 ファイルです。

結果は環境の情報とあわせて記録してください。FSx for ONTAP のスループットキャパシティ、S3 Access Points のネットワークオリジン、リージョン、日付、実行 ID です。デプロイの詳細はツールの [README](../../benchmark/s3ap-throughput/README.md) にあります。
