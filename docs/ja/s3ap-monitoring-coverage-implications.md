## このページの目的

FSx for ONTAP S3 Access Point 経由のアクセスに対して、FPolicy と ONTAP ネイティブ監査ログが
どこまで見えるかは実測で分かれた。その差が設計にどう影響するかを、設計パターンごとに整理する。

測定の内容と条件は
[verification-results-fpolicy-s3ap-and-session.md](verification-results-fpolicy-s3ap-and-session.md)
にある。本ページは測定の記録ではなく、測定から導かれる設計判断を扱う。

## 前提となる測定結果

| 経路 | FPolicy 通知 | FPolicy による遮断 | ONTAP 監査ログ | 監査ログ上の要求者 | ARP による検知 |
|------|------------|------------------|--------------|-----------------|--------------|
| NFS / SMB | 発火する | できる | 記録される | 実ユーザ・実 IP | する |
| S3 Access Point | **発火しない** | **できない** | **記録される** | **記録されない** | **する** |

**機構ごとに答えが違う。** 「ストレージ層の制御は全部効く」も「S3 経路は何も見えない」も
どちらも誤りである。

測定範囲は ONTAP 9.18.1P3D1、UNIX / WINDOWS の両 identity、FPolicy は非同期と
同期 + mandatory の両方、ARP はバージョン 5.0 である。

## 影響を受ける設計パターン

### パターン 1: FPolicy を変更検知フィードに使う

S3 Event Notifications が FSx for ONTAP S3 Access Point で使えないため、代わりに FPolicy を
イベントソースにする構成が広く提案されてきた。**書き込みが S3 Access Point 経由で届く場合、
このフィードは 1 件も流れない。**

書き込みが NFS / SMB 経由なら従来どおり機能する。壊れるのは「S3 で書いて FPolicy で検知する」
という組み合わせだけである。

| 代替手段 | 適する条件 | 制約 |
|---------|-----------|------|
| ONTAP ネイティブ監査ログをフィードにする | 監査ログを既に出している、または出せる。数分の遅延を許容できる | SACL の設定が必要。ログはボリューム上のファイルなので、取り出す経路を別に作る |
| スケジュールポーリング（一覧の差分） | オブジェクト数が中規模で、検知遅延が分単位でよい | 件数に比例して LIST のコストと時間が伸びる |
| 書き込み側でイベントを発行する | 書き込みアプリケーションを自分で持っている | ストレージ層の保証ではなくなる。経路外の書き込みを取りこぼす |
| 書き込み経路を NFS / SMB に寄せる | S3 API である必要が設計上ない | S3 Access Point を使う理由自体を見直すことになる |

### パターン 2: FPolicy をリアルタイムのセキュリティ制御に使う

ランサムウェア検知、DLP、コンテンツ分類、ウイルススキャン連携などを FPolicy 通知で駆動する
構成である。**同じボリュームに S3 Access Point がアタッチされている場合、その経路からの
書き込みは検知器に届かない。** 検知器が観測できない書き込み経路が存在することになる。

これは通知が遅れる問題ではなく、経路が見えない問題である。ただし**用途によって代替がある。**

| 用途 | S3 Access Point 経路での代替 |
|------|---------------------------|
| ランサムウェア検知 | **ARP が使える。** S3 Access Point 経由で書かれた高エントロピーファイルを検知したことを実測した。ファイル内容を見る機構なので経路に依存しない |
| DLP・コンテンツ分類 | ARP は分類器ではないので代替にならない。監査ログを起点にした事後処理か、S3 側での制御になる |
| 操作の遮断 | ストレージ層では表現できない。S3 側（アクセスポイントポリシー、IAM）で行う |
| 変更検知フィード | パターン 1 のとおり |

ランサムウェア検知以外では、次のいずれかになる。

1. リアルタイム制御を要するボリュームに S3 Access Point をアタッチしない。制御の前提を
   ボリューム単位で守る
2. S3 側に別の関門を置く。アクセスポイントポリシーと IAM で、書き込める主体を絞る
3. 監査ログを使った事後検知に切り替える。リアルタイム性は落ちるが、経路は両方見える
4. 影響を受け入れ、S3 Access Point 経由の書き込みが未検知であることを設計文書に明記する

いずれを選ぶ場合も、**「FPolicy を入れたので全経路を見ている」という記述は成り立たない。**
逆に「S3 経路はストレージ層から一切見えない」も誤りで、ARP と監査ログは見ている。

### パターン 3: FPolicy mandatory モードを強制境界に使う

`mandatory=true` は、外部サーバが応答しないときにアクセスを拒否する。ファイルプロトコルに
対してはこれが効く（実測で `Permission denied`）。**S3 Access Point 経由の操作は、同じ
ポリシーの下で PUT / GET / LIST / DELETE がすべて成功した。**

mandatory モードを選ぶ理由は「必ず関門を通す」ことなので、通らない経路が 1 つでもあると
選定の前提が崩れる。強制境界を S3 Access Point 経由の経路にも及ばせたい場合、ストレージ層
ではなく S3 層（アクセスポイントポリシー、IAM、必要ならバケットポリシー相当の制御）で
表現する必要がある。

### パターン 4: 「誰が何にアクセスしたか」を監査ログから答える

S3 Access Point 経由の操作は監査ログに残るが、`SubjectUserName` と `SubjectDomainName` は
`Not Present`、`SubjectIP` は AWS のサービス側アドレスである。**ファイルと操作は分かるが、
要求者は分からない。**

| 求めるもの | 得られるか | 手段 |
|-----------|----------|------|
| どのファイルが、いつ、どう操作されたか | 得られる | ONTAP 監査ログ |
| どの IAM プリンシパルが要求したか | 監査ログからは得られない | S3 Access Point に対する CloudTrail のデータイベント |
| 要求元のネットワークアドレス | 監査ログからは得られない | 同上 |
| ある識別情報に紐づけた粒度 | アクセスポイントの分割粒度まで | アクセスポイントを用途・主体ごとに分ける |

2 つのログを時刻で突き合わせる設計になる。ファイル名で突き合わせると誤る。同じファイルを
後からファイルプロトコルで読むと、その読み取り時刻に同じファイル名の記録が出るためである。

### パターン 5: ONTAP ネイティブ監査ログを S3 経路の可視化に使う

S3 Access Point 経由の操作をストレージ層で捉える手段は、測定した範囲で監査ログと ARP の 2 つ
である。監査ログは全操作を記録し、ARP はランサムウェア様のパターンだけを検知する。
何を知りたいかで使い分ける。監査ログを採用する場合の注意点は次のとおりである。

| 注意点 | 内容 |
|-------|------|
| SACL が必要 | 監査を有効化しただけでは何も記録されない。対象に監査 ACE を適用する |
| `Source` が 3 値ある | オブジェクト操作は `HTTP`、LIST は `S3`、ファイルプロトコルは `CIFS` / `NFS`。1 つの値で絞り込めない |
| HEAD は記録されなかった | 6 回発行して 0 件。存在確認だけの操作は追跡できない可能性がある |
| 要求者は記録されない | パターン 4 のとおり |
| ログはボリューム上のファイル | 取り出す経路を別に用意する。読み取りに NFS を使う場合はクライアント側キャッシュに注意する |

## 選び方

```text
S3 Access Point 経由の書き込みを検知したい
  ├─ リアルタイムに遮断する必要がある
  │    → ストレージ層では表現できない。S3 層（アクセスポイントポリシー / IAM）で行う
  ├─ リアルタイムに検知したいが遮断は不要
  │    → 現時点で手段がない。監査ログによる事後検知に落とすか、書き込み経路を見直す
  └─ 事後に把握できればよい
       → ONTAP ネイティブ監査ログ。SACL を設定し、Source で経路を判別する

S3 Access Point 経由のアクセスの要求者を特定したい
  ├─ ストレージ層のログで完結させたい
  │    → できない。監査ログに要求者は残らない
  └─ ログを 2 本突き合わせてよい
       → 監査ログ（何を・いつ）+ CloudTrail データイベント（誰が）を時刻で対応づける
```

## この判断の有効範囲

| 項目 | 範囲 |
|------|------|
| ONTAP バージョン | `9.18.1P3D1` のみで測定。他バージョンは未確認 |
| identity 型 | UNIX と WINDOWS の両方で同じ結果 |
| FPolicy モード | 非同期、および同期 + mandatory |
| FPolicy モード | 非同期、同期 + mandatory、および接続を受け付けている同期エンジン |
| ARP | バージョン 5.0（学習期間不要の世代）で検知を確認。遮断は未測定 |
| 未確認 | FlexCache キャッシュ側の挙動、ONTAP ネイティブ S3（FSx の S3 Access Point ではないもの）、Vscan のカバレッジ、ARP による遮断 |

Vscan は FPolicy とも ARP とも別の機構であり、**本測定は Vscan について何も述べていない。**
FPolicy が S3 経路を見ないことを、Vscan が見ないことの根拠に使ってはならない。

ARP については逆向きの注意が必要である。検知は実測したが**遮断は測っていない。** 検知できることを
遮断できることの根拠に使ってはならない。また `attack_probability` は書き込みから 10 分以上
遅れて変わるため、この値だけを短時間見て「検知されていない」と判断すると偽陰性になる。
suspect の一覧を見る必要がある。
